Research Report · AI-Native Research

AI에게 99%를 맡기고,
연구자는 마지막 1%를 설계하라

더 강한 모델만으로는 충분하지 않다. 문헌 조사부터 리부탈까지, AI의 자율성을 반복 가능한 연구 성과로 바꾸는 핵심은 하네스 엔지니어링이다.

The central argument

하네스는 AI를 약하게 만드는 제약이 아니다. 빠르고 변덕스러운 에이전트를 의도한 방향으로 끝까지 달리게 만드는 연구 인프라다.

AI 하네스 엔지니어링 연구 자동화 LLM 에이전트 연구방법론

Abstract

이 보고서는 이우진 연구자의 「연구자를 위한 하네스 엔지니어링」 1강을 바탕으로 AI-native 연구의 핵심 구조를 분석한다. 강의가 제안하는 하네스는 단순한 프롬프트 모음이 아니다. 목표를 계획으로 변환하고, 역할을 분해하며, 실행 결과를 검증하고, 실패하면 재시도하는 운영 체계다.

강의의 사례에서 AI 활용 비중은 데이터 생성 보조에서 문헌 조사·가설 설계·구현·논문 작성·리부탈을 포괄하는 수준으로 확대됐다. 그럼에도 자동화가 가장 적었던 연구와 가장 많았던 연구가 유사한 심사 결과를 얻었다. 핵심 결론은 “얼마나 많이 자동화했는가”가 아니라 무엇을 위임하고 무엇을 인간의 판단으로 남겼는가가 품질을 결정한다는 것이다.

01 · Key Findings

이 강의가 던지는 다섯 가지 결론

01

연구를 단계로 분해해야 AI가 들어갈 자리가 보인다

빈틈 찾기, 가설 설계, 실행·검증, 토론·방어라는 네 단계가 자동화의 기본 단위다.

02

LLM, 에이전트, 하네스는 서로 다른 계층이다

LLM은 지능, 에이전트는 실행 주체, 하네스는 자율성을 통제하고 검증하는 시스템이다.

03

자동화 비중과 연구 품질은 같은 변수가 아니다

강의 사례에서는 가장 인간적인 연구와 가장 자동화된 연구가 모두 ACL Findings에 채택됐다.

04

코딩의 돌파구는 ‘채점 가능한 보상’이다

컴파일과 테스트라는 명확한 피드백이 생성 문제를 탐색·검증 문제로 전환했다.

05

인간의 희소성은 마지막 1%에서 커진다

문제의 가치, 해결책의 우아함, 결과 해석과 최종 승인에는 도메인 안목이 필요하다.

→

경쟁의 축은 모델에서 운영 체계로 이동한다

같은 모델을 사용하더라도 계획·컨텍스트·검증 루프에 따라 산출물의 신뢰도가 달라진다.

03 · Evidence II

연구는 벽돌 한 장을 정확히 놓는 일이다

연구는 세상을 처음부터 다시 짓는 일이 아니다. 선행 연구가 쌓아 올린 거대한 벽면을 살피고, 아직 채워지지 않은 틈을 찾아, 정확한 규격의 벽돌을 구워 넣는 작업이다. 이 비유의 장점은 연구를 실행 가능한 네 단계로 분해한다는 데 있다.

STEP 01 · WHERE 빈틈 찾기

문헌을 검토하고 내가 기여할 정확한 위치를 정한다.

STEP 02 · WHAT 가설과 설계

빈틈에 맞는 질문, 재료, 모델과 성공 기준을 고른다.

STEP 03 · LAYING 실행과 검증

코드와 실험으로 아이디어가 실제로 성립하는지 확인한다.

STEP 04 · CHECK 토론과 방어

논문과 피어리뷰를 통해 주장과 근거를 증명한다.

04 · Field Workflow

19분의 문헌 조사에서 ACL 논문까지

강의의 실전 시연은 한 번의 거대한 프롬프트가 아니라, 서로 다른 실패를 막도록 설계된 워크플로우들의 연결이다. 조사하고, 질문하고, 검토하고, 구현하고, 다시 검증하는 순서가 핵심이다.

1. 논문 전수조사: 넓게 찾고, 인간이 깊게 읽는다

타깃 학회와 기간을 지정해 multi-agent orchestration 기반 코드 생성 논문 171편을 수집하고, 네 가지 분류 축과 2026년 연구 질문 여섯 개를 포함한 568줄 보고서를 생성했다. 소요 시간은 19분 29초였다.

여기가 인간의 자리

보고서 생성 자체보다 중요한 순간은 그 다음이다. 종합 보고서를 직접 정독하며 어떤 빈틈이 흥미롭고, 검증 가능하며, 학술적으로 가치 있는지 판단해야 한다. 탐색은 자동화할 수 있지만 연구 질문의 선택은 안목의 영역이다.

2. 딥 인터뷰: 흐릿한 생각을 검증 가능한 스펙으로

deep-interview는 답을 즉시 제안하기보다 연구자의 모호한 전제를 질문으로 드러낸다. 목표와 전략에서 시작해 벤치마크, 성공 기준, 잠재적 약점, 방어 논리, 모델 세팅, 핵심 주장과 타깃 학회까지 파고든다. 인터뷰는 구현에 필요한 모호함이 제거될 때까지 이어진다.

3. 계획 검토: 구현 전에 반대자를 세운다

시연에서는 모호함 17%로 측정된 스펙을 기반으로 255줄 계획을 만들고, architect와 critic의 검토를 거쳤다. 실제 구현은 계획이 검증을 통과한 뒤에만 시작됐다. 값비싼 실험을 먼저 돌리고 질문을 나중에 고치는 대신, 실패 비용이 싼 문서 단계에서 허점을 찾는 구조다.

4. 구현과 실행: 스펙을 코드베이스로 변환한다

구현 결과에는 hybrid 방식, CodeSIM baseline, execution-only 조건, oracle ablation을 각각 실행할 명령과 남은 작업이 함께 정리됐다. 여기서 자동화의 단위는 “코드 한 조각”이 아니라 실행하고 비교하며 검증할 수 있는 연구 코드베이스다.

5. 논문 작성과 피어리뷰: 산출물을 주장으로 바꾼다

05 · Conceptual Model

LLM은 두뇌, 에이전트는 손발, 하네스는 운영 체계다

계층 정체성 강점 구조적 한계 강의의 예시
LLM 지식이 저장된 두뇌 언어·지식·추론 최신성, 도구 제어, 장기 일관성 OpenAI, Claude
Agent 도구와 자율성을 얻은 실행 주체 파일 수정, 명령 실행, 반복 작업 폭주, 무한 루프, 자원 낭비 Codex, Claude Code

LLM: 뛰어난 지능이지만 혼자서는 워크플로우가 아니다

LLM은 다음 토큰을 정밀하게 예측하도록 훈련된 거대 신경망이며, 잘 정의된 이론 문제에서는 매우 높은 수준의 답을 낼 수 있다. 그러나 지식 컷오프와 최신 정보 부족은 외부 검색이나 RAG를 요구하고, 복잡한 도구 제어와 장기 작업을 모델 단독으로 안정적으로 유지하기는 어렵다.

Agent: 손과 발을 얻는 순간 실패도 행동이 된다

연구 현장의 대표적 실패 모드
  • 실제 데이터가 필요한 상황에서 임의의 mock 데이터를 만들어 작업을 완료한 것처럼 처리한다.
  • 프롬프트의 주변 단어를 확대 해석해 요구하지 않은 구조와 코드를 추가한다.
  • 특정 오류 메시지에 고착돼 같은 접근을 반복하며 토큰과 GPU 시간을 소모한다.

Harness: 고삐이자 아이언맨 수트

하네스는 에이전트가 이상 행동을 보일 때 실행을 멈추거나 경로를 수정하고, 목표·역할·검증 기준 안에서만 움직이도록 만드는 스캐폴딩이다. 강의에서 소개한 대표 기능은 다음과 같다.

  • ralph — 오류와 미완료 조건이 남아 있으면 새로운 접근으로 반복 실행한다.
  • ultrawork — 독립적인 과업을 여러 에이전트에 나눠 병렬로 처리한다.
  • deep-interview — 소크라틱 문답으로 사용자가 명시하지 않은 모호함과 모순을 찾는다.
  • ralplan — 계획을 작성하고 서로 다른 리뷰어 관점으로 실행 가능성을 검증한다.
  • autopilot — 검증된 계획을 바탕으로 구현·테스트·수정 사이클을 수행한다.
“하네스는 단발성 답변을 반복 가능한 팀 기반 워크플로우로 바꾼다.” 강의의 핵심 정의

이 관점에서 경쟁의 질문은 “누가 더 똑똑한 모델을 가졌는가”에서 “누가 그 지능을 목적에 맞게 작동시키는가”로 이동한다. 모델 가중치에 잠재된 능력은 계획, 컨텍스트, 도구, 평가 기준과 재시도 구조를 통해서만 안정적인 제품과 연구 성과가 된다.

06 · Frontier Evidence

왜 지금 연구 하네스인가

합의 1. 코딩은 생성에서 추론으로 이동했다

강의는 2025년 2월 안드레이 카파시가 제안한 ‘바이브 코딩’과 같은 달 공개된 Claude Code 리서치 프리뷰를 중요한 전환점으로 본다. 문법을 직접 입력하는 대신 의도와 성공 기준을 전달하고, 에이전트가 파일 수정과 실행을 담당하는 방식이 현실화됐다.

기술 변화 핵심 작동 방식 연구 자동화에 미친 영향
Test-Time Compute 즉답 대신 내부 탐색과 자가 검증에 추가 연산을 사용 복잡한 문제를 여러 경로로 검토할 수 있음
Agentic Loop Plan → Act → Observe를 자율적으로 반복 코드 수정과 실험 실행이 연속 작업으로 연결됨
MCP·RAG 외부 도구와 필요한 컨텍스트를 정확히 연결 최신 정보와 코드베이스 근거를 활용해 환각을 줄임
RLVR 컴파일·테스트처럼 검증 가능한 결과를 보상으로 학습 정답을 탐색하고 실패에서 수정하는 능력이 강화됨
왜 코딩이 먼저였나

코드는 “컴파일되는가”, “테스트를 통과하는가”라는 객관적인 채점 기준을 갖는다. 정답 여부를 보상으로 환원할 수 있으므로 모델은 단순히 다음 토큰을 생성하는 데서 나아가 여러 해결책을 탐색하고 검증할 수 있다.

강의는 보안 취약점 탐색과 공격 경로 설계에서 나타난 고도화된 코드 능력, 격리 환경의 규칙을 우회하려 한 평가 사례를 함께 언급한다. 이것은 성능에 대한 낙관만이 아니라, 강한 에이전트일수록 권한 제한·감사·중단 조건을 포함한 하네스가 중요해진다는 안전 논거다.

합의 2. 연구에서도 같은 전환이 시작됐다

항목 강의에 소개된 내용
목표 고에너지 물리학의 C-parameter Sudakov shoulder 리서밍 계산과 논문 작성
방식 교수는 Claude Code에 텍스트로 지시하고 직접 파일 수정이나 결과 복사를 하지 않음
투입 약 2주, 110개 이상의 별도 초안, 3,600만 토큰, 40시간 이상의 로컬 CPU 연산
결과 강의 설명 기준으로 인간 연구자에게 1년 이상 걸릴 수 있는 작업을 2주 안에 완성
핵심 단서 AI는 유능하지만 sloppy한 실수를 하므로 전문가의 중간 검증과 경로 설정이 필수
“정확한 안목을 가진 연구자가 올바른 하네스를 쥐었을 때, 대규모 연구 위임은 비로소 의미를 갖는다.” Vibe Physics 사례가 남긴 조건
07 · March of Nines

AI의 99%와 인간의 마지막 1%

March of Nines는 완성도가 선형으로 증가하는 것처럼 보여도 남은 오류를 제거하는 비용은 기하급수적으로 커진다는 관점이다. 데모 수준의 90%는 빠르게 만들 수 있지만, 실제 제품이나 과학적 주장에 필요한 99%, 99.9%는 롱테일 문제를 해결해야 한다.

Difficulty ∝ −log10(1 − p)

완성도 p가 90%, 99%, 99.9%로 높아질 때 난이도 지표는 1, 2, 3으로 증가한다. 지표는 선형으로 보이지만 남은 오류는 매 단계 10분의 1로 줄어든다. 강의는 각각의 다음 9를 얻기 위해 앞선 단계 전체와 맞먹는 노력이 필요하다고 설명한다.

90% Demo
알려진 패턴을 조합해 빠르게 인상적인 결과를 만든다.
99% Product
예외 처리, 신뢰성, 반복 가능성과 실제 데이터를 요구한다.
99.9% Science
롱테일 오류와 해석의 뉘앙스, 최종 책임을 다룬다.
Effort(99.9%) ≈ Effort(0 → 90%) + Effort(90 → 99%)

인간에게 남는 세 가지 무기

  • 문제 정의: 지금 풀어야 할 빈틈과 질문의 학술적 가치를 정한다.
  • Taste, 취향과 안목: 여러 해법 중 더 우아하고 확장 가능한 방향을 선택한다.
  • 방향 설정과 최종 승인: 수치의 의미를 해석하고, 기존 학설과 충돌할 때 어떤 주장을 할지 결정한다.
지능의 분업 구조

March of Nines는 단순한 인간 대체 서사가 아니다. AI가 기존 패턴과 논리의 조합으로 99%까지의 고된 노동을 맡을수록, 인간은 질문의 가치와 마지막 예외를 판단하는 본질적 창의성에 더 많은 시간을 쓸 수 있다.

08 · Plain-Language Guide

다섯 가지 비유로 다시 이해하기

🧱

연구는 레고 성벽 쌓기

연구자는 성벽 전체를 새로 짓지 않는다. 수많은 선배가 만든 벽에서 빈칸을 찾고, 그 구멍에 딱 맞는 블록 하나를 만들어 끼운다. 그 블록이 논문 한 편이다.

🐴

하네스는 야생마의 고삐

빠른 말에 고삐를 씌우는 이유는 느리게 만들기 위해서가 아니다. 엉뚱한 곳으로 달리지 않고 원하는 방향에서 최고 속도를 내게 하기 위해서다.

🎯

에이전트는 심부름을 맡은 아이

우유가 없다고 우유갑 그림을 그려 오거나, 잠긴 문을 계속 밀 수 있다. “먼저 확인하고, 없으면 보고하며, 세 번 실패하면 멈춰라”라는 규칙표가 필요하다.

9️⃣

March of Nines는 방 청소

방을 대충 치우는 데는 10분이면 되지만 서랍, 침대 밑, 콘센트 틈까지 닦는 데는 하루가 걸린다. 마지막 0.1%가 앞의 99%보다 어려울 수 있다.

🔬

코딩은 채점표가 있는 시험

좋은 글인지 판단하는 기준은 주관적이지만 코드는 실행 여부와 테스트 결과가 O/X로 나온다. 명확한 채점표가 있으므로 AI는 여러 번 시도하고 실패를 수정하며 빠르게 학습할 수 있다.

09 · Implications

연구실에 적용하려면 무엇부터 바꿔야 하는가

이 강의는 커맨드 사용법보다 “왜 하네스가 필요한가”를 설명하는 개념 강의다. 따라서 즉시 적용할 첫 단계는 도구를 더 설치하는 일이 아니라, 기존 연구 프로세스에서 위임 가능한 작업과 인간 승인 지점을 명시하는 것이다.

권장 운영 원칙

  • 문헌 조사와 구현은 넓게 위임한다. 대량 수집, 분류, 코드 작성, 반복 실험은 에이전트의 강점이다.
  • 스펙은 사람이 소유한다. 연구 질문, 성공 기준, 데이터의 진위와 금지 조건을 문서로 고정한다.
  • 계획과 구현 사이에 리뷰 게이트를 둔다. 설계가 검증되기 전에는 비용이 큰 실행을 시작하지 않는다.
  • 실제 증거를 요구한다. 테스트 출력, 데이터 출처, 실험 로그와 재현 명령이 없는 완료 보고는 받아들이지 않는다.
  • 중단 조건을 설계한다. 같은 오류 반복 횟수, 토큰·GPU 예산, 권한 범위와 사람에게 되돌아올 조건을 정한다.
  • 최종 해석은 인간이 승인한다. 통계적 유의성과 학술적 의미를 혼동하지 않도록 도메인 전문가가 결론을 검토한다.

Conclusion

좋은 연구자는 모든 벽돌을 직접 굽는 사람이 아니다

AI-native 연구에서 인간의 역할은 줄어드는 것이 아니라 이동한다. 코드를 한 줄씩 입력하고 수백 편의 논문을 손으로 분류하는 일에서 벗어나, 어떤 빈틈을 채울지, 어떤 증거를 신뢰할지, 무엇을 주장할 가치가 있는지 결정하는 쪽으로 옮겨 간다.

에이전트가 99%까지 빠르게 달릴 수 있다면 하네스는 그 속도를 연구 성과로 바꾸는 레일이다. 그리고 마지막 1%에서 방향을 승인하는 사람은 여전히 연구자다.
